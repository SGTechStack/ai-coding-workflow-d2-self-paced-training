Lesson 1 of 2 — Eitri Agentic Dev Workflow ✦ Hands on

What Was Built on Top of Matt Pocock

Matt Pocock's workflow covers the full idea-to-ship cycle but does not sequence stories in dependency order, enforce architectural boundaries in code, apply government compliance policies, or verify that tickets are well-specified before implementation begins. Eitri adds each of these checks at the step in the workflow where it belongs.

By the end of this lesson you will know:
  • How to sequence stories in dependency order using /dependency-orchestrator
  • How to enforce architectural boundaries and apply compliance policies using /arch-tests-plan and /spec-compliance
  • How to verify ticket quality using /issue-verification before implementation begins
  • How to execute the self-steering developer loop using /do-work
Pre-requisite setup for this hands-on lesson

To internalise the workflow, you can run through each skill hands-on in your own repository. Install the Eitri skills on top of your existing Matt Pocock setup before starting:

Eitri is a suite of custom AI skills built on top of Matt Pocock's foundational five-phase workflow (Architecture, Specification, Decomposition, Implementation, and Closeout). While the baseline workflow is strong, applying it to a government enterprise environment exposes four critical gaps that Eitri fills:

How Eitri fills the gaps

Gap 1: No build sequencing ➔ /dependency-orchestrator [+]

Without sequencing, teams guess what to build first. In Phase 1 (Architecture), Eitri maps out dependencies across your stories to generate a PM delivery report (estimates & critical path) and a developer wave plan before any code is written.

Gap 2: Architectural drift ➔ /arch-tests-plan & /arch-tests-gen [+]

Nothing stops code from drifting between layers. Eitri converts your architectural boundaries into automated, build-failing tests. If a developer violates a rule, the build fails immediately rather than waiting for a code review.

Gap 3: Missing compliance checks ➔ /spec-compliance [+]

Catching a security violation during the specification phase is a simple document edit; catching it later causes massive rework. In Phase 2, Eitri automatically audits the TRD against policies like IM8 and ARC before the TRD Sign-off gate.

Gap 4: Vague ticket instructions ➔ /issue-verification [+]

An agent stalls on vague tickets. In Phase 3, Eitri verifies that every ticket covers all layers, is demoable, and has unambiguous criteria before publishing them to the tracker and advancing to the Ticket Sign-off gate.

Bonus: The Self-Steering Loop ➔ /do-work [+]

The baseline implement skill runs in a single pass. In Phase 4, Eitri wraps implementation in a self-steering engine: build (TDD) ➔ AI code review ➔ automated quality gates. If any check fails, the engine instantly triggers a fix-and-retry loop until every gate is green.

Phase 5 Closeout ➔ /arch-tests-gen-feature [+]

Takes the placeholder architecture rules generated by the arch-tests-plan skill in Phase 1 and fills them in with the real package names from the newly built feature, converting theoretical boundaries into automated tests.

The sections below walk through each Eitri skill in workflow order — what gap it fills, what it produces, and how it connects to the next step. Each section maps to a phase in the diagram above.

Implementation Loop

11
/do-work [+]
Self-steering feedback loop — Implement → Review → Validate → Mutation → Commit
/do-work — The Self-Steering Implementation Loop ~ 3–4 min
Video Recap

Implementation alone lacks compliance, security scanning, and framework-specific standards. The /do-work skill wraps implementation in a self-correcting loop to guarantee every commit is secure, standardized, and fully compliant.

The Five-Phase Loop

The skill maps out a five-step execution plan: Implement → Review → Validate → Mutation Gate → Commit.

Automated Validation ➔ code-reviewer

Once the initial review clears, the Validate step launches the full code-reviewer skill suite in parallel. This covers builds, maintainability (e.g. duplicated logic), static analysis (e.g. React array keys), org compliance (IM8 logging gaps), and framework conventions (JUnit vs native asserts), generating a consolidated HTML report.

Self-Correction Mechanism

The agent does not stop if blockers are found. The workflow loops those blockers directly back to the Implement phase, automatically applying corrections. It only halts for human guidance if it fails to fix the same issue twice.

Mutation Gate

Before committing, the workflow advances to the Mutation Gate, seeding small defects into the code to prove the tests actually catch them.

Faster Feedback for Manual Fixes

If you want to iterate quickly on a failure without running the full suite, you can run individual checks directly on your current diff (e.g., /code-reviewer im8, /code-reviewer semgrep).

Customising /do-work for your stack
Calibrate the agent to your team's standards before your first sprint
Customising /do-work for Your Stack ~ 3–4 min
Video Recap

The loop ships with defaults. Before you start, calibrate the workflow to match your project's stack, compliance needs, and quality bar.

1. Tailor the Quality Gates ➔ code-reviewer

By default, skills/code-reviewer/SKILL.md runs every registered check. Trim this table to match your exact architecture. If you're building a purely Java backend, remove the react check. If it's a throwaway prototype, remove the strict im8 compliance gate.

2. Enforce Build Thresholds ➔ build-check

Inside skills/build-check/SKILL.md, set strict quality gates such as mandating 80% instruction coverage for Java or 80% test coverage for TypeScript. The build check will block commits until these standards are met.

3. Define Coding Conventions ➔ CODING_STANDARDS.md

The code-review check (powered by Matt Pocock's review skill) relies on CODING_STANDARDS.md at your repository root. Document your naming conventions and anti-patterns here. The agent reads this file during every run to enforce your custom rules automatically.

4. Configure the KB Router ➔ kb-router.md

The KB router maps code signals to Bedrock knowledge base prefixes so /do-work retrieves the right docs automatically. Add entries for any internal SDK or framework not already covered (e.g., mapping Singpass imports to your SingpassSDK knowledge base).

5. Optional: Husky Hooks

If running the full reviewer suite slows down your local iteration loop, you can remove it from the do-work skill entirely and wire up your essential checks as Husky pre-commit hooks instead.

Grilling Before Gates

✋
/grill-me [+]
Alignment check — surfaces hidden assumptions before each HITL gate

Throughout all planning and sequencing steps, you can optionally run Matt Pocock's /grill-me command after any artefact-generating skill. This interactive session acts as a Human-in-the-Loop (HITL) checkpoint to proactively challenge assumptions and ensure perfect alignment with your intent before advancing to the next phase.

HITL Gate 1: TRD Sign-off

Run /grill-me after specification generation to stress-test your Technical Requirements Document (TRD). Once you are satisfied, signing off marks the TRD as approved and clears it for decomposition into tickets.

HITL Gate 2: Ticket Sign-off

Run /grill-me after ticket verification to confirm the full issue set covers all edge cases and dependencies. Once approved, the tickets transition to execution-ready and implementation can begin.

Knowledge check

Check Your Understanding — 11 Questions

1. What three specific components are provided by the AppStandards repository to enforce organisational conventions?

Why (b) is correct: The AppStandards repository provides design decisions/patterns, implementation recipes, and grilling questions for the agent to reference. It is a documentation and recipe library, not a repository for CI/CD infrastructure (a), security testing tools (c), or application tests (d).

2. What critical planning artefact does /dependency-orchestrator produce before any code is written?

Why (a) is correct: /dependency-orchestrator builds a DAG-based wave plan — the story-sequencing layer Matt Pocock's harness has no equivalent of. Option (b) describes /spec-compliance, (c) describes /arch-tests-gen, and (d) describes /to-tickets.

3. How does /arch-tests-gen prevent architectural drift from slipping through code review?

Why (b) is correct: /arch-tests-gen translates documented ADRs into executable boundary tests (ArchUnit/dependency-cruiser) that fail the build if violated, catching drift automatically. It does not rely on the AI reviewer catching it (a), Semgrep rules (c), or manual visual approvals of dependency graphs (d).

4. Why does /spec-compliance run at Step 7 — before /to-tickets at Step 8?

Why (c) is correct: A TRD flaw caught at Step 7 costs one edit; caught post-implementation it costs a rework sprint. Options (a), (b), and (d) describe dependencies between steps that don't exist — ArchUnit tests don't require the compliance report, and /to-tickets doesn't check labels before running.

5. Which three axes does /issue-verification use to vet issues, and which internal skill does it rely on?

Why (d) is correct: The three axes are verticality, demoability, and well-specifiedness. The internal skill is /fry-me. Options (a), (b), and (c) each substitute incorrect axis names or the wrong internal skill.

6. What is the primary purpose of the /grill-me skill before entering a HITL gate?

Why (c) is correct: /grill-me acts as a Socratic challenger to surface hidden assumptions and align decisions before you hit a formal HITL gate. It does not automatically fix code (a), generate HTML reports (b), or bypass human review (d).

7. What is the specific exit condition for the /do-work self-steering loop?

Why (b) is correct: The convergence condition is Must-fix = 0 and all compile, test, coverage, and compliance gates green — not any single gate alone. Unit tests passing (a) is just one gate. Mutation threshold (c) is one gate. HITL Gate 2 (d) is a planning-phase gate that runs before /do-work begins, not as its exit condition.

8. Why is the /mutation-testing gate specifically scoped to changed files rather than the entire codebase?

Why (c) is correct: Scoping to changed files keeps the gate fast per feature slice — fast enough to run on every loop iteration without slowing delivery. Option (a) describes a side-effect, not the design intent. Options (b) and (d) describe mechanisms that don't match how the mutation and coverage gates work inside the loop.

9. You need to check only IM8 security controls on a changeset, without running all other reviewers. Which invocation is correct?

Why (a) is correct: /code-reviewer im8 targets the IM8 Application Technical Controls reviewer specifically. standards (b) checks repo-convention compliance via CODING_STANDARDS.md. semgrep (c) scans for injection and secrets patterns. springboot (d) runs all eight Spring Boot specialist reviewers — more than you asked for.

10. When customising the /do-work skill for your stack, what is the purpose of the skills/do-work/common/kb-router.md file?

Why (a) is correct: The KB router maps codebase signals (like a specific SDK import) to a Bedrock knowledge base prefix, allowing /do-work to proactively retrieve the right documentation. It is not used for network routing (b), PR assignments (c), or endpoint configuration (d).

11. /arch-tests-gen (Step 4) uses <feature> placeholders in boundary tests. What does /arch-tests-gen-feature (Step 13) specifically add?

Why (b) is correct: /arch-tests-gen-feature replaces <feature> placeholders with real package and folder names for the slice just built. Option (a) describes extending the rule plan — that's /arch-tests-plan. Option (c) describes regenerating the full dependency-cruiser config. Option (d) describes recompiling from updated ADRs — that's /arch-tests-gen.
