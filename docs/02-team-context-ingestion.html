Injecting Your Team's Context

The Eitri workflow relies on your team's unique requirements to generate accurate results. Without them, the agent will fall back on generic training data. This lesson covers the Five-Phase Context Injection Model, showing you exactly what context to provide, where it belongs in your repository, and how to inject it so the harness produces outputs perfectly tailored to your project.

By the end of this hands-on lesson you will know:
  • Where and when to inject your team's specific context across the five phases of development
  • The exact files, formats, and repository structures each Eitri skill expects to read
  • How to set up and maintain your team's context repositories to ensure the agent always follows your standards
Why context injection matters

The Eitri workflow is a general-purpose engine. If you do not provide it with your team's specific context, it will fall back on generic training data, resulting in:

  • User stories that miss your domain vocabulary and target the wrong personas.
  • Implementation plans that violate your architectural boundaries and schedule dependencies in the wrong order.
  • Technical specifications that bypass your agency's compliance controls, forcing costly rework later.
  • Source code that suffers from deprecated API calls, build failures, and type errors due to stale training data.
  • Code reviews that allow local anti-patterns and convention violations to pass through silently.

Injecting the right context at the right phase ensures every agentic skill generates outputs perfectly aligned with your project's unique requirements.

Five-Phase Context Map

Overview: The Five-Phase Context Injection Model ~ 4–5 min
Video Recap

Every phase shares one rule: your context must be ready before its corresponding skill runs. If you skip context injection, the workflow falls back on generic training data, baking architectural flaws and compliance violations into your project.

What to inject at each phase

Phase 1: Business Context

Use speckit.constitution or wayfinder to define your domain vocabulary in constitution.md or CONTEXT.md. Without this, the agent invents its own generic workflows and misidentifies your personas.

Phase 2: Architecture Standards

Add your core boundaries to the dependency-orchestrator foundation templates, and map your technical standards in configs/standards.md. This ensures the correct standards are automatically linked to every story in your delivery schedule.

Phase 3: Security & Governance

IM8 and ARC policies are built-in. Add any custom agency policies to the policies skill's references/ folder and register them in its SKILL.md. Run this before /spec-compliance to catch gaps before they become code.

Phase 4: Coding Best Practices

Upload your framework versions, design system, and internal SDKs to an AWS Bedrock Knowledge Base. Map them in kb-router.md so the do-work skill can retrieve the exact documentation it needs just-in-time.

Phase 5: Code Review Standards

Define your team's naming, architectural, and security conventions in CODING_STANDARDS.md at the repository root. Matt Pocock's review skill uses this file to flag every violation. You can also extend the automated suite in code-reviewer/SKILL.md.

Phase What to inject Skill(s) that consume it Cost of skipping
1. Requirements Business domain intent, persona maps, scope boundaries /speckit-specify, /wayfinder, CLARA Agent designs the wrong features and user stories miss domain vocabulary
2. Application Architecture Standards Shared architecture standards, integration recipes, ADR templates /dependency-orchestrator, /wayfinder Stories are decomposed without structural constraints, causing upstream architectural flaws to propagate into every ticket
3. Compliance Regulatory and security policies (IM8, ARC, custom) /spec-compliance, /policies Policy gaps survive into implementation, requiring a rework sprint
4. Implementation Coding best practices, framework guides, API reference docs /do-work (via /query-kb → Bedrock) Agent writes code against stale training-data APIs, resulting in build failures and type errors
5. Execution & Code Review Repository coding style, quality gate thresholds, Registered Checks /code-reviewer, /do-work Agent runs the wrong suite of checks, and convention violations pass through undetected
Shift before the phase — the core injection rule

Context must be ready before the workflow step that consumes it. A compliance policy written after /spec-compliance has already run won't be audited. An OKF standard registered after /dependency-orchestrator won't appear in the Dev Delivery Plan. Treat the five phases above as a preparation checklist, not a reactive one: complete each phase's setup before invoking the corresponding skill.

Business Domain & Requirements
Inject your business domain context before user stories are generated
Phase 1 — Injecting Business Domain & Requirements Context ~ 3–6 min
Video Recap

The goal of Phase 1 is to ground the agent in your domain context before a single user story is written. Without this grounding, it defaults to generic assumptions (e.g., writing stories for "customers" instead of "Registration Clerks"). There are three paths to set this up:

Path 1: Spec-Kit

Run the speckit.constitution skill to define your domain terminology and business rules, which creates a constitution.md file. Then, invoke speckit.specify with the feature you want to build, your actual end users, and the scope of the release. Every subsequent Spec-Kit command will automatically read the constitution file.

Path 2: Socratic (Matt Pocock)

Create a CONTEXT.md file with your domain vocabulary at the repo root and run the setup-matt-pocock-skills skill. When you invoke wayfinder, it begins an interactive grilling session grounded in your domain vocabulary. As decisions crystallise, the domain-modeling skill automatically records emerging terms in your CONTEXT.md file.

Path 3: CLARA (Product Research)

Ensure your team's domain documentation is uploaded to your Confluence spaces. CLARA queries these spaces to ground its User Personas, Journey Maps, and specification files in your actual business context.

Deep Dive: Path 2 (Matt Pocock Approach)

To skew the model effectively, create a CONTEXT.md file at the repository root containing:

1. Glossary

Establish exact terminology using a "not" column (e.g., Attendance, not visit) to prevent the agent from substituting generic equivalents.

2. Systems

Map out external integrations (e.g., CDLENS) to explicitly define where your application's responsibility ends.

3. Data Model

Name key entities and how they relate (e.g., separating TOCCScreening as a distinct entity from a triage assessment).

4. Personas

Define actual end-users and their goals (e.g., a Charge Nurse who needs real-time monitoring).

5. Scope

Clearly define what is included and excluded (e.g., deferring Singpass to Phase 2) to prevent the agent from hallucinating out-of-scope workflows.

With CONTEXT.md in place, invoke wayfinder. Because its reasoning is now skewed by your requirements, every question it asks during the interactive grilling session will strictly use your domain terminology, forcing every generated ticket to speak the exact language of your project.

Phase 2 — Injecting Application Architecture Standards ~ 3–6 min
Video Recap

The harness aligns user stories with standard implementation recipes during dependency orchestration and wayfinding. This requires the AppStandards base library, and optionally your team's own additional standards.

1. Clone AppStandards
Terminal
git clone https://github.com/SGTechStack/App-Standards

The AppStandards library covers: Logging, File Management, Interface & Batch, User Access Control, MFA, MCC Platform Services, and Reporting. For the EMR project, the orchestrator will automatically flag User Access Control (Standalone) and Logging (General) as relevant to every story that touches patient data.

2. Add Custom Team Standards (optional)

If your team maintains standards beyond AppStandards (e.g., internal FHIR profile rules, hospital-specific audit log schema), structure them using the Open Knowledge Format (OKF):

OKF layout — your custom standards repo
standards-emr/
  index.md               ← concept catalog (agent reads this first)
  fhir-profiles/
    index.md             ← FHIR-specific concept catalog
    patient-resource.md   ← strict rules + code recipes
    encounter-resource.md
  audit-logging/
    index.md
    emr-audit-schema.md   ← audit log field rules for EMR
3. Register in the Orchestrator

Add your standard's path-mapping entries into APPFW_STANDARD_REFS in skills/dependency-orchestrator/report-generator.py:

skills/dependency-orchestrator/report-generator.py
APPFW_STANDARD_REFS = {
    # ... existing AppStandards entries ...
    "EMR_FHIR":      "../standards-emr/fhir-profiles/index.md",
    "EMR_AUDIT":     "../standards-emr/audit-logging/emr-audit-schema.md",
}
4. Tag Stories with Standard Keys

In your user story files, tag the appfw_standard field so the orchestrator maps each story to its relevant standards:

spec.md — Patient Registration story (excerpt)
## US-01: Register Patient
appfw_standard: [USER_ACCESS_CONTROL_STANDALONE, LOGGING_GENERAL, EMR_AUDIT]

As a front-desk staff member, I want to register a new patient...

The Dev Delivery Plan will then include the relevant standard sections for developers to reference during /wayfinder, without them having to search the entire standards catalog.

How to add a custom policy

1. Write your policy as a Markdown file. Structure it as a checklist of controls:

skills/policies/references/emr-data-governance.md
# EMR Data Governance Policy

## DG-01: Patient PII Retention
Patient PII must not be retained beyond 7 years from last clinical encounter.
TRD must declare the data retention period and deletion mechanism.

## DG-02: Cross-border Data Transfer
Patient data must not be transmitted outside Singapore data centres without MOH approval.
TRD must declare all data residency constraints.

## DG-03: Diagnosis Code Audit Trail
Any modification to an ICD-10 code must generate an immutable audit log entry
with before/after values, actor ID, and timestamp.

2. Register it in skills/policies/SKILL.md so the compliance agent loads it during audits.

Use /policies for targeted manual checks

If you only need to check a single control (rather than running the full compliance agent), use /policies. It loads the policy Markdown references without spinning up the full audit. Useful when authoring a new policy or verifying a single TRD section.

Coding Best Practices (AWS Bedrock KB)
Upload current library docs so the agent doesn't fall back on training data
Phase 4 — Setting Up the AWS Bedrock Knowledge Base ~ 3–4 min
Video Recap

If you do not connect the agent to an external knowledge base, it falls back on static training data—resulting in deprecated methods, type errors, and API calls that no longer exist.

1. The Trap: Context Rot

Loading your entire standards library and framework documentation upfront exhausts the LLM's context window. Recall accuracy degrades silently, causing the agent to hallucinate or miss critical instructions.

2. The Solution: Hybrid Retrieval

Pre-load only the global context the agent always needs (e.g., coding standards, ticket spec). Everything else is retrieved just-in-time and injected exactly when the agent encounters the relevant code.

3. What to Upload to Bedrock

Upload anything the agent would otherwise have to guess at: design system docs, framework guides, internal API references, and approved coding patterns.

4. The Mechanism ➔ kb-router.md

The router maps specific code signals to the AWS Bedrock KB. For example, opening a React .tsx file triggers the router to retrieve your Shadcn guidelines and accessibility requirements, injecting them at the point of need.

skills/do-work/common/kb-router.md — custom entry for Singpass SDK
- signal: "import.*singpass"
  prefix: SingpassSDK
  description: Singpass MyInfo SDK patterns and approved integration methods
5. Environment Configuration

Connect the agent to the right knowledge base by setting three simple environment variables:

Terminal — required environment variables
export AWS_REGION="ap-southeast-1"
export BEDROCK_KB_TAG_KEY="project"
export BEDROCK_KB_TAG_VALUE="emr-system"
5
Code Review Standards
Configure the code-reviewer dispatcher and define your team's coding conventions
Phase 5 — Code Review Standards ~ 3–4 min
Video Recap

At the end of every implementation loop, the code-reviewer skill acts as a dispatcher, launching an entire suite of automated checks that run in parallel against your code changes.

1. The Parallel Dispatcher

By default, it runs build validation, security analysis (Semgrep), IM8 controls, framework checks, and Matt Pocock's code review. All results are aggregated into a single HTML compliance report.

2. Extending the Suite ➔ code-reviewer/SKILL.md

To register a new check (e.g., mutation testing), simply add a row to the table in code-reviewer/SKILL.md. The dispatcher will automatically include it in every subsequent run.

3. The Two-Axis Code Review

Matt Pocock's review skill uses two independent sub-agents to eliminate blended verdicts. The Specification Axis verifies that your code faithfully implements the originating ticket, while the Standards Axis ensures it adheres to your team's documented conventions.

4. Defining Your Rules ➔ CODING_STANDARDS.md

For the Standards Axis to enforce your specific engineering rules, create a CODING_STANDARDS.md file at your repository root. Define naming conventions, architectural patterns (e.g., mandating AuditLogger over standard SLF4J), and security conventions here.

CODING_STANDARDS.md (EMR project, excerpt)
# EMR Coding Standards

## Naming
- Patient-facing DTOs: suffix `Request` (input) / `Response` (output)

## Architecture
- All audit events must be routed through the custom `AuditLogger` class, not standard SLF4J.
- No `Optional.get()` without `isPresent()` check (use `orElseThrow()`)
