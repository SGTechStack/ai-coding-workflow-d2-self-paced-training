Lesson 0 — PO Workflow

From User Stories to Delivery Plan

This lesson walks through the full Product Owner (PO) journey in the Eitri Agentic Dev Workflow, covering how to elicit fine-grained user stories with stakeholders, generate a dependency-sequenced delivery plan with the Tech Lead, sync completed work into GitHub, and validate the system end-to-end.

By the end of this lesson you will know:
  • What makes a fine-grained, testable user story and how to elicit one
  • How to run /dependency-orchestrator with the Tech Lead to produce a PM delivery report
  • How to read the PM report: team size, timeline, critical path, and risk
  • How to use /stories-to-issues to create structured GitHub issues before Wave 1 starts
  • How to use /reconcile-stories to sync closed GitHub issues back into the delivery plan
  • How to validate the system against acceptance criteria during the end-to-end testing phase
Who is this lesson for?

This lesson is written for Product Owners (POs) who collaborate with a Tech Lead to plan and track delivery. Your role is to provide business requirements, review the generated delivery plans, and validate the final system, while the Tech Lead operates the underlying agentic tools.

  • PO Provides inputs and reviews outputs during story elicitation (Phase 1), delivery planning (Phase 2), and progress reconciliation (Phase 5). Leads end-to-end acceptance testing (Phase 6).
  • Tech Lead Operates all the agentic tooling to generate the plans and issues: /dependency-orchestrator (Phase 2), /stories-to-issues (Phase 3), and /reconcile-stories (Phase 5).
  • Developer Owns the actual coding and implementation (Phase 4), which is covered separately in Lesson 1.

Phase 1 — Eliciting Fine-Grained User Stories

1
Working with stakeholders to define fine-grained, testable user stories
Each story must describe one user capability with clear, verifiable acceptance criteria. The more specific the story, the more accurate the delivery plan and estimates will be.

In the agentic workflow, user stories are the primary input that drives the delivery schedule. The skill works backwards from each story's end state to determine every development task needed and how they depend on each other. Vague or incomplete stories produce unreliable plans.

The three properties that matter most

Story Properties
Testable Every story must have acceptance criteria that can be verified by running an automated test or by a human manually checking that the described behaviour works end-to-end.
Vertically sliced Each story must cut through all layers (data, logic, UI) and be demo-able independently. Horizontal slices ("build the database schema") cannot be tested as a standalone unit and prevent the delivery tool from ordering work accurately.
Fine-grained One story = one user capability. If you can split a story and the two halves can each be tested independently, split it. Coarse-grained stories produce vague implementation sequences and inaccurate estimates.

Example: good vs problematic stories

Good — vertically sliced, testable
"As a nurse, I can register a new patient with their NRIC, name, and date of birth so that the patient has a record before clinical assessment begins."
Acceptance Criteria:
1. Submitting valid details creates a patient record and shows a confirmation.
2. Duplicate NRIC is rejected with a clear error message.
3. Missing required fields are flagged inline before submission.
Problematic — horizontal slice, not independently testable
"As a developer, I want to build the patient database schema so that patient data can be stored."
Why it fails: This is an implementation task, not a user capability. It cannot be demoed. The delivery tool requires every story to have a verifiable end state that a non-developer can check.

Using /grill-with-docs or /wayfinder to sharpen stories

Before finalising your story list, run it through one of these skills with the Tech Lead. Both will surface ambiguities that would otherwise only appear mid-implementation:

SkillBest used whenWhat it produces
/grill-with-docs You have a rough idea and want to think it through. The skill interviews you to extract requirements and challenges assumptions Architecture Decision Records (ADRs) and a domain glossary alongside a refined story list
/wayfinder You have a complex, multi-path problem with several unknowns that need to be resolved as decision tickets A set of decision tickets resolved one at a time, producing a clear route through the complexity
Food for thought
  • A stakeholder says "we need a reporting module." How do you turn that into fine-grained user stories?
    Ask: who uses this report, what decision does it drive, and what does "done" look like for them? That conversation typically produces 3–5 separate stories: one for generating a fixed report, one for filtering, one for exporting, and so on. Each can be demoed independently. The word "module" is a feature area. Never accept a feature area as a single story.
  • Why can't you put infrastructure tasks ("set up CI/CD", "create the database") as user stories in the input list?
    Infrastructure tasks are automatically handled by the dependency orchestrator using foundation templates. The skill derives them from the platform you declare and attaches them as infrastructure stories internally. If you add them as feature stories too, you create duplicates in the delivery plan and distort the schedule. Your input list should contain only user-visible capabilities.
  • What is the risk if a story's acceptance criteria are vague ("the form should work correctly")?
    Vague acceptance criteria propagate through to the GitHub issue, the developer's implementation prompt, and the E2E test. At each step, the agent and the developer have to guess what "correctly" means. The result is either an over-engineered feature (developer hedges by building everything) or a partial implementation (developer builds only what was obvious). Fine acceptance criteria are the contract. Without them, delivery quality is non-deterministic.

Who does what in this phase
  • Tech Lead: opens a terminal in the project directory, types /dependency-orchestrator, and selects PM when asked for role.
  • PO: sits alongside (or shares screen) and provides all the answers to the interview questions the skill asks. No command-line knowledge is required.

What to prepare before the session

  • Your finalised list of user stories (from Phase 1), each with acceptance criteria, saved as a file
  • A view on whether all stories are one release or should be split into sequential releases
  • Any known sequential constraints you are already aware of (e.g., "Reporting can only start after Patient Intake is complete")
  • Optional: a grouping of stories by business value area (e.g., "Patient Intake", "Discharge Flow", "Reporting") and which areas are highest priority. If skipped, the skill will place all stories in a single default group

The interview questions the skill asks

The skill conducts a structured interview before building the delivery plan. The questions are always asked in this order:

/dependency-orchestrator — PO Interview Questions
1. Project name What is the project called? Used as the report title.
2. Platform(s) Which stacks apply? (Web frontend / Mobile / Backend API / combinations). This determines which foundation templates are loaded. Do not skip stacks that are genuinely in scope.
3. User stories file Provide a file path, document link, or MCP resource pointing to the stories from Phase 1. Do not paste stories inline. The skill requires a file path so it can process them without loading the entire list into its context.
4. Release planning Should all stories be treated as a single release, or broken into sequential releases (2–3 month chunks)? If sequential, the skill will ask you to group stories by release (e.g., "Release 1: stories 1–80, Release 2: stories 81–120"). Each release gets its own delivery plan. Later releases only start once earlier releases are fully complete.
5. Known constraints Any hard sequential dependencies you already know about? (e.g., "Reporting can only start after Patient Intake is complete"). These ordering rules are built into the delivery plan.
6. Optional components Do any of these apply to your project? Database migrations (Alembic, Flyway, Liquibase), CI/CD pipeline setup, App Store setup (mobile only). Answer yes / no / unsure for each.
7. Business value groups (optional) Group the stories by feature / business area (e.g., "Patient Intake", "Checkout Flow", "Reporting"). You can specify which stories belong to each group, or skip this step. If skipped, all feature stories are placed in a single default group. Infrastructure stories are always grouped as "Platform Setup".
8. Group priorities (only if Q7 answered) Are any groups higher priority than others? Valid values: critical, high, normal (default), low. Priority propagates to all stories in the group and affects scheduling order. Higher-priority stories are scheduled before lower-priority ones, even when they have the same schedule buffer.
The skill asking the PO interview questions
The skill interviews the PO before building the delivery plan. Stories must be provided as a file path or document link, not pasted inline, to keep the skill's context lean.

What the skill does after the questions are answered

The skill processes the PO's answers in several steps that run automatically. It takes roughly 3–5 minutes depending on the number of stories:

  • Backwards mapping: for each story, the skill traces the dependency chain backwards from the story's end state to the foundation layer, deriving every dev task required and its dependencies
  • Dependency graph construction: all tasks and edges are merged into a single project-dag.json file, deduplicating shared foundation tasks across stories
  • Scheduling analysis: the skill runs Critical Path Method (CPM) analysis once to identify which tasks must happen in sequence and which can run in parallel. It then separately simulates the delivery timeline for different team sizes, from 1 developer up to the point where adding more gives no further benefit, to find the optimal staffing level. The critical path itself does not change with team size. Only the overall delivery duration does
  • Report generation: the PM report is written to pm-report.html and its key metrics are summarised in the conversation
Adding stories later (add-on mode)

If stakeholders add new requirements after the initial plan is produced, re-run /dependency-orchestrator. The skill detects the existing plan, asks whether to merge the new stories in (add-on mode) or start fresh, and re-generates the full report with the combined picture. The critical path and delivery date are recomputed from scratch.

Food for thought
  • The skill asks for "business value groups". Why can't it figure out the groupings automatically from the story titles?
    Business value groupings reflect stakeholder priorities and organisational ownership, not just vocabulary similarity. Two stories that both mention "patient data" may belong to different business domains: one to patient intake (owned by clinical operations) and one to reporting (owned by management). The skill will propose groupings based on domain nouns, but you must confirm them because the grouping affects which stories are prioritised in the scheduler and how risk is reported per business area.
  • What does it mean to say the skill uses "backwards mapping" to derive dev tasks from a story?
    Backwards mapping starts at the end state described by the story (e.g., "patient receives triage assessment") and traces the chain of structural prerequisites backwards: what must exist before the end state can be reached? That chain reveals every dev task the story requires and in what order those tasks must be completed. This is how the delivery schedule is derived from user stories rather than from a separate estimation exercise.
  • Why is team size NOT asked during the PO interview, and who sets it?
    The PM report is designed to be resourcing-neutral: it shows you the delivery timeline for every possible team size, so you can make the resourcing decision based on the trade-offs (cost vs speed). Team size is only fixed when the Tech Lead generates the developer report — at that point a specific team size is chosen and the Gantt chart is rendered for it. This separation means the PO can explore "what if we add two more developers?" without re-running the full analysis.

Reading the PM Report

The PM report is written for stakeholder communication, not for developers. It deliberately omits implementation chains and wave scheduling. What it shows you is the information you need to make resourcing decisions and set delivery expectations.

Key metrics and team size options

The stats bar at the top of the report is interactive. The PO selects a team size from the dropdown and an estimate type (optimistic, likely, or pessimistic), and the estimated duration updates to reflect that choice. The remaining figures — max useful developers, total stories, and risk concentration — are fixed values derived from the delivery plan. The team size table below the stats bar shows the full duration breakdown for every staffing level, from 1 developer up to the point where adding more gives no further benefit. Use it to negotiate resourcing with management.

PM Report — stats bar and team size table
The stats bar lets the PO adjust team size and estimate type to see how the duration changes. The team size table below shows the full breakdown across all staffing levels.
What each part of the report shows
Team size A dropdown to select how many developers are on the team. Defaults to the recommended team size. Changing it updates the estimated duration immediately.
Estimate A slider with three confidence levels: Optimistic (no added buffer), Likely (+15% buffer), and Pessimistic (+30% buffer). Use Likely as the default when communicating to stakeholders. Switch to Pessimistic when setting a deadline commitment.
Est. duration How many working days the project will take at the selected team size and confidence level. This is the number to present to stakeholders as the delivery estimate.
Max useful developers The recommended team size — the last point where adding one more developer saves at least one working day. Adding developers beyond this number does not shorten delivery because the planned sequence of tasks leaves extra developers waiting.
Total stories The total number of stories in the plan, including both infrastructure and feature stories. Use this to confirm all user stories from Phase 1 were included, and to give stakeholders a sense of project scope.
Risk concentration Critical path effort as a percentage of total effort. High risk concentration (above ~60%) means most of the project's delay risk sits on a single chain of stories. Any slippage on that chain directly delays the delivery date with no schedule buffer to absorb it.
Team size table A table showing the estimated delivery duration for every team size, from 1 developer up to the maximum useful number. Each row also shows how much time that additional developer saves compared to the row above. Use this to present the cost-vs-speed trade-off to management when negotiating resourcing.
Potential blockers Highlights the stories most likely to cause delays: the primary bottleneck story (the one that unblocks the most downstream work), the critical path chain, the story with the longest wait relative to its own effort, and waves where parallel stories outnumber available developers. Use it to decide where to assign senior developers and where to add buffer time.

Effort and completion charts

The PM report includes three charts that help set stakeholder expectations about capacity and delivery shape.

PM Report — effort and completion charts
Top: the S-curve of stories becoming testable over time, with per-business-value-group progress visible on hover. Bottom left: effort split by technical category (frontend, backend, infrastructure, testing, design). Bottom right: infrastructure scaffolding versus user-visible feature work as a percentage of total effort.
What each chart tells you
Stories completed over time A cumulative count of stories becoming testable across the delivery window. An S-curve shape is normal: slow at the start while infrastructure is built, accelerating through the middle waves, then tapering as the final stories complete. A flat early period is expected: infrastructure stories are being built first, unblocking everything that follows.
Effort by technical category Total effort broken down by frontend, backend, infrastructure, testing, and design. Use this to validate that the team skill mix matches where the effort actually sits. If 60% of effort is backend but the team is frontend-heavy, that is a resourcing risk to raise early.
Infrastructure vs feature work The percentage of total effort spent on platform scaffolding (auth, CI/CD, database setup) versus user-visible features. A high infrastructure percentage early in the project is expected and normal. Use this to set stakeholder expectations: visible progress will be limited until the infrastructure wave is complete.

Story readiness timeline

The story readiness timeline lists each user story in the order it becomes testable, showing its earliest testable day and business value group. The dates adjust automatically when the team size is changed. Use this to plan QA windows, schedule stakeholder demos, and set interim milestones.

PM Report — story readiness timeline
Stories are listed in the order they become testable. Critical path stories are highlighted. Use the testable dates to schedule QA sessions and plan stakeholder demos.

How to use the report in stakeholder conversations

  • Present the estimated duration and team size as a range: "With X developers we deliver in Y weeks. With X+2 we deliver in Z weeks. Here is the cost difference."
  • Use the risk concentration to set expectations: "Over 60% of the project's delay risk sits on the critical path stories. We need to ring-fence those stories from scope changes."
  • Point at the critical path stories when stakeholders ask about schedule risk. Any delay to those stories directly moves the end date.
  • Use the story readiness timeline to schedule QA milestones and interim demos at the points where business value groups become testable.
Food for thought
  • A stakeholder says "can't we just add more developers to finish faster?" What does the PM report tell you?
    The team size table shows exactly how many developers the plan can actually absorb. Beyond the max useful developers number, additional developers sit idle because some tasks must happen in sequence and cannot be split across extra people. You can show the stakeholder the table and explain: "Beyond N developers, extra people end up waiting on others to finish before they can start. Adding more people past this point extends the budget without shortening the timeline."
  • What does high risk concentration (e.g., 72%) mean for how you manage the project?
    It means 72% of the total effort sits on the critical path: stories with no schedule buffer. Any delay to any of those stories directly delays the project end date with no room to absorb slippage. Protect those stories from scope changes, avoid reassigning their developers, and front-load QA for those stories so defects are found early. Low-risk-concentration projects are more forgiving; high-concentration projects require tighter control of a small number of key stories.
  • The estimated completion says "15 working days". What does that mean in calendar weeks, and what does the PM report not tell you?
    15 working days is 3 calendar weeks assuming no public holidays or leave. The PM report assumes 100% developer availability and does not account for leave, public holidays, code review turnaround, or release/deployment overhead. Add 20–30% as a realistic buffer when communicating a delivery date to stakeholders. The report is a planning baseline, not a guaranteed commitment.

Phase 3 — Creating GitHub Issues with /stories-to-issues

Before Phase 3: Tech Lead generates the developer delivery plan

The PM report from Phase 2 showed delivery durations across all possible team sizes so the PO could negotiate resourcing with management. Once a specific team size is agreed, the Tech Lead re-runs /dependency-orchestrator in Developer role. Because the full dependency analysis was already completed in Phase 2, the skill skips all planning questions and asks only for the agreed team size. How the Tech Lead runs it

Terminal — project root 
/stories-to-issues

The skill asks for: the path to processor-output.json (the single output file from the dependency orchestrator), the target GitHub repo, the team size to use for scheduling data, any labels to add to all issues, and whether to do a dry run first. Always confirm the dry run output before creating real issues. Once created, issues cannot be automatically deleted.

Why the acceptance criteria in the issue are verbatim

The skill copies your original acceptance criteria into the GitHub issue without any summarisation or rephrasing. This is deliberate: the acceptance criteria in the issue are the same contract you agreed with the stakeholder in Phase 1. Any rewording risks silently changing the definition of done. When a developer closes this issue, they are asserting they have met your original criteria.

Food for thought
  • Why are issues created in Gantt scheduling order rather than alphabetically or by feature group?
    Creating issues in Gantt order means the issue list on GitHub naturally reflects the implementation sequence. Issue #1 is the first story a developer should pick up. It also makes it easy to verify the plan at a glance: if the issue list looks wrong (e.g., a dependent story appears before its dependency), it signals an error in the delivery plan that should be resolved before development starts.
  • A developer asks "do I have to follow the dev tasks listed in the issue exactly?" How would you answer?
    The dev tasks are the implementation steps derived from the delivery plan. They represent the minimum chain of work required to deliver the story. Developers can use their professional judgement on how to implement each task, but they cannot skip tasks without disrupting the plan's assumptions. If they discover a task is unnecessary or should be split, the right action is to flag it via a comment on the GitHub issue and notify the Tech Lead. The Tech Lead can then rerun /dependency-orchestrator in add-on mode to update the plan.

Phase 4 — Developer Implementation

4
Monitoring story progress and keeping the delivery on track
Developers work through GitHub issues wave by wave. The PO's role is to track progress against the story readiness timeline, resolve blockers on critical path stories, and keep stakeholders informed.

With GitHub issues created in Phase 3, developers pick them up in wave order and work through each story using the developer delivery report (dev-report.md) as their guide. Your role as PO is to monitor progress, protect the delivery date, and keep stakeholders informed.

What "waves" mean for the PO

Waves are dependency-derived groupings — all stories in a wave are unblocked and can run simultaneously. Use the wave structure when planning stakeholder demos and QA check-ins. Every story in a wave should be testable before the next wave begins.

The PO's role during implementation

  • Monitor wave completion: track which GitHub issues are closed, open, or blocked, and communicate status against the story readiness timeline from the PM report
  • Protect the critical path: any blocker on a critical path story needs immediate escalation as it directly shifts the delivery date
  • Defer new requirements: if stakeholders request changes mid-delivery, capture them as new stories for a follow-on cycle. Injecting new stories mid-wave can disrupt the planned sequence and make existing estimates unreliable
  • Prepare for QA: schedule QA sessions for each wave completion using the story readiness dates from the PM report
Food for thought
  • A developer says "Story X is blocked because Story Y isn't done." What does this tell you about the delivery plan?
    It tells you either: (a) the dependency between Y and X was correctly captured in the plan and Y is behind schedule, which is a scheduling problem, or (b) the dependency was missing from the plan entirely, which means the original plan was incorrect. In case (a), the critical path analysis tells you whether delaying Y delays the whole project. In case (b), re-run /dependency-orchestrator in add-on mode to incorporate the discovered dependency and regenerate the plan.
  • A stakeholder asks to add a new story mid-way through Wave 2. What should you do?
    Accept the requirement but defer it. Add it to the backlog, complete Wave 2, then re-run /dependency-orchestrator in add-on mode. The skill will merge the new story into the existing plan, identify where it fits in the delivery sequence, and update the PM report. Injecting mid-wave changes risks disrupting in-progress work and breaking developer focus. The cost of the disruption always exceeds the perceived urgency.

Phase 5 — Reconciling Completed Stories with /reconcile-stories

5
Reconciling completed stories to keep the delivery plan current
As developers close GitHub issues, the Tech Lead runs /reconcile-stories to mark stories as done, update delivery projections, and regenerate the PM report with actual progress.
Tech Lead runs the skill at the end of each wave, or whenever the PO needs an updated delivery projection

As developers complete stories and close their GitHub issues, the original delivery plan becomes stale. /reconcile-stories pulls the current state of those issues into the plan: completed stories are marked done, the schedule for remaining stories is recomputed, and updated PM and dev reports are generated with accurate projections.

What changes and what does not

Reconciliation — what changes
Unchanged The story dependencies and their order. Reconciliation never changes which stories depend on which. Only the timing is updated.
Updated Completed stories no longer count towards remaining work. The schedule is recalculated based on actual progress and a revised projected finish date is produced.

What the reconciled reports show

  • Progress bar: stories done vs remaining, and whether the project is ahead or behind the original schedule
  • Completed story markers on each finished story, showing the actual GitHub issue close date
  • Updated Gantt chart reflecting remaining work only, with completed stories appearing faded
  • Revised projected finish date based on remaining effort and current team velocity

How to run it

Terminal — project root 
/reconcile-stories

The skill asks for: the location of the dependency orchestrator's output files, the GitHub repo, team size, labels to filter issues by (use auto-generated to match only issues created by /stories-to-issues), the project start date, and where to write the reconciled reports. Always confirm the dry-run output first. It shows how many stories mapped to issues and how many are closed.

When to run it

Run at the end of each wave to give stakeholders an updated picture before the next wave begins. Also run it any time someone asks "where are we?" The reconciled report answers with actual progress data, not the original estimate.

Issues must be created by /stories-to-issues first

/reconcile-stories maps closed issues back to stories by parsing the story ID from the issue title (format: STORY-ID: title). It only works if the issues were created by /stories-to-issues. Manually created issues with different title formats will not be matched.

Food for thought
  • A developer closes a story's GitHub issue but the code is still in review. Should you count it as complete in the reconciliation?
    No. A closed issue signals a completed story — closing it is an assertion that the acceptance criteria have been met, not that code has merely been submitted for review. Establish a team convention: issues are only closed after the code review is approved, the changes are merged, and automated tests pass. Closing early inflates the progress bar and distorts the remaining schedule projection.
  • After reconciliation, the projected finish date has moved later than the original estimate. What should you tell stakeholders?
    Be direct: the original estimate was a plan based on assumptions. The reconciled projection is based on actual progress. If stories are taking longer than estimated, the updated projection is more accurate than the original. Use the progress bar to show what proportion of work is done, and the updated Gantt to show which stories remain on the critical path. Stakeholders need the accurate picture, not the reassuring one.

Phase 6 — E2E Testing & Acceptance

6
Verifying each story meets its original acceptance criteria through E2E tests and manual review
E2E tests verify the technical integration. Manual acceptance verifies the user experience against the original acceptance criteria. Both are required before declaring a story done.

When all GitHub issues from Phase 3 are closed and automated tests pass, the project enters the acceptance phase. Closing a GitHub issue is the formal handoff from the dev team to you, signalling that a story's acceptance criteria are met. This is the PO's primary gate: does the application actually deliver the value described in each user story?

Two layers of verification

Acceptance — two layers
E2E tests Automated tests that start the application and simulate real user flows end-to-end. They verify that the technical layers (API, database, UI) integrate correctly. A passing E2E test suite confirms the application does not crash on the happy path. It does not verify that the UX is good or that edge cases are handled correctly.
Manual acceptance The PO opens the running application and walks through each story's acceptance criteria manually. This catches mismatches between what was technically built and what was described: error messages that are technically correct but confusing, flows that work but are in the wrong order, or features that are present but not discoverable.

How to run the acceptance walkthrough

For each user story (working through the story readiness timeline from the PM report, earliest first):

  1. Open the GitHub issue for the story. Its acceptance criteria are your checklist
  2. Start the application (the Tech Lead or a developer can help if needed)
  3. Walk through the scenario described in the story as a real user would
  4. Verify each acceptance criterion. Check the happy path, then the edge cases listed
  5. Note any discrepancies as comments on the GitHub issue. Distinguish between genuine defects (the criterion is not met) and new requirements (the criterion is met but you want something different)
Defect vs new requirement: the critical distinction

During acceptance, it is easy to conflate two very different findings:

  • Defect: the application does not meet an acceptance criterion that was agreed in Phase 1. This is a bug. The developer must fix it before the story is closed.
  • New requirement: the application meets all acceptance criteria, but you now want additional behaviour. This is a new story for the next cycle. Do not reopen the issue or expand its scope mid-acceptance.

If you cannot distinguish them, go back to the acceptance criteria you wrote in Phase 1. If the criterion is there and not met, it is a defect. If the criterion is not there, it is a new requirement.

When all stories pass acceptance

Once every story's acceptance criteria are verified and all E2E tests pass, the project is ready for User Acceptance Testing (UAT) with real end users or a controlled release. At this point the delivery is complete from an engineering perspective. What follows is an operational decision about release timing, not a technical one.

Food for thought
  • A developer says "all E2E tests pass, so the stories are done." Is that sufficient? What is the PO's response?
    No. E2E tests verify technical integration: that the layers connect and the application does not crash on the happy path. They do not verify that the UX matches the acceptance criteria, that error messages are correct, or that the feature is discoverable by a real user. The PO acceptance walkthrough is always required before a story is closed, because the tests verify what was coded and the PO verifies what was actually needed.
  • During acceptance you find that a field label is confusing and you want it renamed. Is this a defect?
    Only if the acceptance criterion specified the exact label text. If the criterion says "the form must display the patient's NRIC field with an appropriate label", and the current label says "ID Number", you can argue it does not meet "appropriate" and raise it as a defect. But if the criterion says only "the patient registration form must submit successfully", renaming the label is a new requirement. Be precise about what the acceptance criteria say — that is the contract.
  • Why should the acceptance walkthrough use the story readiness timeline order rather than testing stories in any order?
    The story readiness timeline reflects the dependency order of the project. Stories that other stories depend on appear first. If you accept stories in dependency order, any defect found in an early story (e.g., the patient registration story) can be fixed before you test the stories that depend on it (e.g., the triage story). Testing in a random order risks discovering a foundational defect after you've already "accepted" the stories that depend on the broken foundation.
