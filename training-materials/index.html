How this aligns with our direction toward SPDD

Our organisation is moving toward Structured-Prompt-Driven Development (SPDD) from ThoughtWorks, which requires attending a paid course. Matt Pocock's workflow is a strong alternative that aligns to the same spec-driven development principles. Since the Eitri skills are grounded in spec-driven development principles, they apply directly within an SPDD workflow, so nothing needs to change.

Why Matt Pocock's framework?
  • Specification-first, specification as authority: a dedicated skill interviews you to produce a complete specification before any code is written, and that specification remains the source of truth throughout. When code and specification diverge, the specification wins. This directly addresses intent drift, the root failure mode of AI-assisted coding.
  • Composable and lightweight: provides small, focused skills deployed only when necessary. Each skill is designed to prevent a specific AI coding pitfall (such as skipping tests or losing track of context) without imposing a heavyweight process or replacing your engineering judgment.
  • No toolchain lock-in: compatible with any AI coding tool (Claude Code, Cursor, Cline) and any team setup, without imposing fixed directory structures or workflow conventions.
  • Built around real failure modes: every workflow decision addresses the primary ways AI coding fails (ambiguity, intent drift, and poor handoff quality) and is grounded in decades of engineering practice, not theoretical best practice.

Workflow summary — what you just learnt

Matt Pocock's agentic workflow is built around these skills, each invoked as a slash command.

/setup-matt-pocock-skills
Configure the issue tracker, triage labels, and domain doc layout. Run once per repo.
/grill-with-docs or /wayfinder
Sharpen a plan through structured interview, creating Architecture Decision Records (ADRs) and a domain glossary as you go (/grill-with-docs), or map a complex effort as decision tickets, resolving one at a time (/wayfinder)
/to-spec
Synthesise the conversation into a Product Requirements Document (PRD) and publish it to the issue tracker
/to-tickets
Break a spec, plan, or conversation into tracer-bullet tickets with blocking edges on the issue tracker
/implement
Implement using TDD where applicable, closing with a code review before committing
/code-review
Review on two axes: Standards (conventions + code smells) and Spec (faithfulness to the originating issue or PRD, including scope creep)
/diagnosing-bugs
Use at any point to diagnose hard bugs and regressions using a structured 6-phase loop

    /wayfinder maps a complex effort as decision tickets and resolves them one at a time, producing a clear route to implementation. /to-spec then synthesises that conversation into a Product Requirements Document (PRD) and publishes it to the issue tracker.

LLM & Agent Foundations
Four topics that give you the foundation to understand, extend, and refine the workflow, serving as the basis for the customisations taught in Lessons 1 and 2.
Topic 1 How LLMs Actually Work
Context Windows, Smart Zone / Dumb Zone, and Lost in the Middle
The context window is the total text (prompt, instructions, code, conversation history) the model can see in a single call. Models perform reliably up to roughly 40% of their context limit (the Smart Zone). Beyond that, they enter the Dumb Zone where reasoning quality degrades. Within any window, content buried in the middle is recalled less accurately than content at the start or end (the Lost in the Middle effect).
LLM Memory Architecture
LLMs have no persistent state between calls. Three memory stores: in-context (the current prompt and conversation, ephemeral and lost between calls), external (durable artifacts like files, version control, and issue trackers that persist across sessions), and parametric (the model's trained weights, fixed and unchangeable). The workflow relies on external memory as its durable backbone.
Hallucination and Non-determinism
Hallucination: LLMs predict the most likely next token, not verify facts, so they generate plausible but incorrect information with confidence. This is a generation problem, not a placement problem. No amount of Smart Zone positioning can prevent it. The safeguards are human review and automated tests that catch incorrect outputs. Non-determinism: identical inputs produce different outputs across runs. Machine-verifiable tests, not eyeballing output, are the only reliable convergence signal.

Food for thought
  • What is the Smart Zone, and what does the Lost in the Middle finding tell you about where to place critical information in the context window?
    The Smart Zone is the first ~40% of a model's context limit, where reasoning is most reliable. Lost in the Middle shows that even within a well-sized window, content buried in the middle is recalled less accurately than content at the start or end. Place critical instructions at the top of the context and avoid burying key reference material in the middle.
  • What are the three LLM memory stores, and which one does the workflow rely on to persist state across sessions?
    In-context (the current prompt and conversation, ephemeral and lost between calls), external (durable artifacts like files, version control, and issue trackers that persist across sessions), and parametric (the model's trained weights, fixed and unchangeable). The workflow relies on external memory (decisions, specs, and ADRs written to the repo) to persist state across sessions.
  • What is the difference between hallucination and Lost in the Middle? Can placing reference material in the Smart Zone fully prevent hallucinations?
    Lost in the Middle is an attention problem: the model recalls content placed in the middle of a long window less accurately. Hallucination is a generation problem: because LLMs predict the most likely next token rather than verify facts, they can produce incorrect outputs even when given correct reference material. Smart Zone placement helps attention, but cannot prevent hallucination.
  • Why does non-determinism make "it looks right" an unreliable convergence signal? What should you rely on instead?
    LLMs use stochastic sampling, so identical inputs produce different outputs across runs. A response that looks correct once may be wrong on the next run. Machine-verifiable tests, which pass or fail deterministically, are the only reliable signal that the loop has converged correctly.
Topic 2 Agentic Engineering
Prompt Engineering
Writing clear, targeted instructions for individual agent calls. Effective prompts use role framing (set the agent's expertise and perspective), positive framing (describe the target behaviour, not what to avoid, because LLMs predict tokens toward whatever pattern you surface), chain-of-thought elicitation (ask the model to reason step by step), and explicit completion criteria (define what "done" looks like).
Context Engineering
Where Prompt Engineering focuses on how you phrase instructions, Context Engineering focuses on what information is in the context window at every step. Context rot degrades recall silently as the window fills, even before it's full. The design principle: pre-load only what's always needed, and retrieve everything else just-in-time.
Retrieval-Augmented Generation (RAG)
Fetches relevant knowledge from an external index at inference time instead of pre-loading everything into the context window. Source documents are chunked, indexed, and searched on each request (semantic, keyword, or hybrid). The most relevant chunks are injected into the context window just-in-time. This is the mechanism that powers the retrieve-on-demand principle in Context Engineering.
Open Knowledge Format (OKF)
A structured knowledge representation that makes retrieval more precise than raw document chunks. Andrej Karpathy argued that conventional RAG retrieves noisy, unstructured text fragments. Hybrid search (combining semantic and keyword search) helps find the right chunk, but the chunk itself may still contain irrelevant surrounding text. OKF addresses this at the representation level by organising knowledge as typed entities and relationships, so the unit of retrieval is a specific fact rather than a block of text.
Model Context Protocol (MCP)
An open protocol for connecting AI models to external tools, data sources, and services. Where RAG retrieves from a pre-indexed snapshot, MCP lets the agent connect to external tools and query their current state: reading file systems, calling APIs, querying databases, and more, without custom integration per tool.
The ReAct Pattern and Agentic Loop Design
The pattern that turns a single-shot LLM into a multi-step agent. The agent cycles through three phases: Reason (decide what to do next), Act (call a tool, write code, or run a command), and Observe (read the result and feed it back into the next reasoning step). This observe-then-reason loop is what lets agents self-correct based on real outcomes rather than guessing in a single pass. Every loop needs a convergence condition that tells it when to stop (e.g. all tests pass, zero must-fix findings). Without one, two failure modes emerge: the loop runs indefinitely with no signal to terminate, and each observation cycle adds to the context window, progressively degrading recall.
Planning-Execution Separation
Complete all research, questioning, and planning before writing any code. When planning and execution are interleaved, three failure modes emerge:
  • Context overflow: researching mid-task eats up token limits that should be reserved for writing code.
  • Plan narration: the agent gets confused and just describes what it would do instead of actually coding.
  • Late requirement changes: ambiguities surface mid-implementation and derail the coding session.
In Matt Pocock's workflow, QRSPI (Questions → Research → Structure → Plan → Implement) puts this into practice by completing the first four steps before any code is written.
Agent Skills
Reusable agent capabilities packaged as SKILL.md files containing instructions, scripts, and resources, each invoked via a slash command. Progressive disclosure keeps the context footprint minimal: only each skill's name and one-line description load at startup. Full instructions load only when a skill is actually invoked, so adding more skills does not bloat every session. This is how Eitri extends Matt Pocock's workflow without modifying its core.

Food for thought
  • What is the difference between role framing and positive framing? Why does telling a model what to do produce more reliable results than telling it what to avoid?
    Role framing sets the agent's context and expertise ("you are a senior TypeScript engineer"), orienting all responses from that perspective. Positive framing describes the target behaviour rather than prohibitions: "always write typed interfaces" rather than "never use any". Because LLMs predict the next most likely token rather than reason about constraints, stating a prohibition still surfaces the unwanted pattern in the model's attention. Positive framing gives the model a clear target to generate toward.
  • What is context rot, and why can't you pre-load all your framework guides into every session?
    Context rot is the silent degradation of model recall as the context window fills, happening before the nominal token limit is reached. Pre-loading all framework guides consumes context capacity that should be reserved for the actual task, and causes recall to degrade across everything else in the window. The fix is to retrieve only what's needed just-in-time.
  • What is the difference between RAG and OKF? Why does retrieval quality improve when you move from raw document chunks to structured knowledge?
    RAG fetches text chunks from an external index at inference time. Hybrid search (semantic + keyword) improves which chunk you find, but the chunk itself may still carry irrelevant surrounding text. OKF goes further by structuring knowledge as typed entities and relationships rather than unstructured text, so the unit of retrieval is a precise fact rather than a paragraph. As Karpathy argued, the noise problem isn't just about finding the right document; it's about what that document contains.
  • What can MCP do that RAG cannot? What does this mean for how an agent accesses information it wasn't trained on?
    RAG retrieves from pre-indexed, static knowledge stores; it cannot interact with live systems or read state that changes between sessions. MCP lets the agent connect to external tools and query their current state: querying a database for current records, calling an API for up-to-date data, or reading a file system as it exists right now. Together, RAG handles stable reference knowledge while MCP handles dynamic, current-state access, without bespoke integration code for every tool.
  • Why does a ReAct loop need an explicit convergence condition? What happens without one?
    A convergence condition is an objective, machine-verifiable signal that tells the loop when to stop (e.g. all tests pass, zero must-fix findings). Without one, the loop has no signal to stop. Each Reason → Act → Observe cycle feeds new observations back into the context, progressively filling the window until the model degrades into the Dumb Zone or hits the context limit, and the agent keeps looping without making meaningful progress.
  • What three failure modes does Planning-Execution Separation prevent? Why do they occur when planning and execution are interleaved?
    • Context overflow: researching mid-task eats up token limits that should be reserved for writing code.
    • Plan narration: the agent gets confused and just describes what it would do instead of actually coding.
    • Late requirement changes: ambiguities surface mid-implementation and derail the coding session.
    Keeping the phases separate eliminates all three.
  • What is a SKILL.md file, and how does progressive disclosure keep the context footprint minimal as the number of installed skills grows?
    A SKILL.md defines a reusable agent skill: its name, a short description, and detailed instructions, along with supporting scripts and resources. Progressive disclosure means only the name and one-line description of every installed skill load at startup. Full instructions only load when a skill is actually invoked, so installing more skills doesn't proportionally increase the context footprint of every session.
Topic 3 Agentic Development Principles
Human-in-the-Loop (HITL) Design
Because AI agents will confidently guess answers to ambiguous requirements rather than pause, you must place human review at defined checkpoints where decisions require judgment (scope changes, compliance sign-off). Let the system self-correct only where the outcome is machine-verifiable (syntax errors, test failures). A gate that can be bypassed, even accidentally, is not a gate.
Specification-First Development
A complete, unambiguous specification must exist before implementation begins: the agent reads and implements rather than deriving requirements mid-loop. Several approaches exist, each with a different way of expressing that specification:
  • Behaviour Driven Development (BDD): using human-readable scenarios as the spec
  • Spec-Driven Development (SDD): a formal specification document drives all downstream work
  • Structured Prompt Driven Development (SPDD): structured prompts as the spec format
  • Spec Kit: structured spec templates for AI agents
  • Get Shit Done (GSD): a lightweight spec-first framework
  • Obra Superpower: spec-first workflow tooling
  • Default Coding Agent's Plan Mode: the built-in planning step in tools like Claude Code before execution begins

Why was Matt Pocock's workflow chosen for Eitri? Because it is incredibly lightweight and flexible. While agentic frameworks like Spec Kit or GSD mandate specific directory structures, multi-file templates, and dedicated CLIs, Pocock's workflow simply relies on a folder of composable, conversational skills. You only invoke the skills you need (like /grill-me). The agent actively interviews you to extract requirements and then generates a single plan.md. It gives you the discipline of a spec-first process with near-zero overhead and no rigid lock-in.

Test-Driven Development (TDD)
TDD follows the Red-Green-Refactor loop: write a failing test (Red), write the minimum code to make it pass (Green), then refactor without breaking tests (Refactor). In agentic work, TDD provides the machine-verifiable convergence signal: the loop exits when tests pass, not when output looks plausible. Without it, non-determinism means there is no objective way to know the agent is done.
Architecture Decision Records (ADRs)
Short documents capturing a technical choice (context, decision, consequences). Because agents have no persistent memory between sessions, ADRs stored in version control act as their durable external memory. Without them, a future agent session has no way to know a past architectural choice was deliberate, and may silently "fix" or reverse it. Storing them in the repo ensures every new session encounters them.
Tracer Bullet Development
A strategy for slicing work into tickets. Rather than building horizontal layers (e.g. building the entire database schema first), work is sliced vertically into a thin, production-quality feature that cuts through all layers (data, logic, interface, tests). It is essential for agents because horizontal slices cannot be demoed or tested end-to-end in isolation. If a slice can't be fully tested, the agent cannot verify its own output, and the self-correction loop stalls.
Living Documentation
In traditional development, stale documentation is an annoyance. In agentic development, it is a fatal bug. Because agents treat your repository's documentation as their system prompt, they will faithfully generate code that perfectly complies with whatever standards they read. If your documented architecture constraints and coding standards drift from reality, the agent will confidently produce wrong outputs.

Food for thought
  • What distinguishes a decision that needs human judgment from one the system should self-correct? Give an example of each.
    Because agents will guess rather than pause when faced with ambiguity, human judgment is required for decisions involving scope changes or compliance sign-off, as these are things the system cannot objectively verify. The system should only be allowed to self-correct where the outcome is purely machine-verifiable, like a failing test or a syntax error.
  • What is the core principle of Specification-First Development, and why is Matt Pocock's workflow considered more lightweight and flexible than frameworks like Spec Kit?
    The core principle is that a complete specification must exist before implementation begins so the agent implements rather than deriving requirements mid-loop. While frameworks like Spec Kit mandate specific directory structures and dedicated CLIs, Matt Pocock's workflow is lightweight and flexible because it simply uses a folder of composable conversational skills (like /grill-me) to dynamically co-create a single plan document. You only invoke what you need, avoiding heavy toolchain lock-in.
  • Why does TDD provide a more reliable convergence signal than checking whether output looks correct?
    Because of non-determinism, output that looks correct on one run may differ on the next. A passing test suite is machine-verifiable: the loop exits only when a defined, objective standard is met, not when a human or the agent judges the output to look right.
  • What three fields does an Architecture Decision Record contain, and why does storing it in version control matter for future agent sessions?
    Context (why the decision was needed), decision (what was chosen), and consequences (what this implies going forward). Because agents have no persistent state, storing ADRs in version control acts as their external memory. It ensures future sessions encounter them when reading the repo, preventing the agent from silently "fixing" or reversing deliberate decisions made in earlier sessions.
  • What is a tracer-bullet issue and why must it touch all architectural layers?
    A tracer-bullet issue is a vertically sliced ticket: a thin but production-quality feature that cuts through every layer (data, logic, interface, tests). It must touch all layers because horizontal slices (like building just the DB schema) cannot be demoed or tested end-to-end in isolation. If it can't be fully tested, the agent has no objective way to validate its own output.
  • What happens to an agent's outputs when the coding standards it was given are out of date?
    Because agents treat documentation as their system prompt, they will faithfully generate code that perfectly complies with whatever standards they read. If those standards are outdated, the agent will confidently produce wrong outputs. In agentic development, documentation isn't just a guide; it is executable configuration that must stay current.
Topic 4 Multi-Agent Patterns
Orchestrator-Worker Architecture
The orchestrator coordinates (sequences work, routes blockers) and never reads files or makes implementation decisions. An orchestrator that does implementation work fills its context with detail and loses coordination accuracy.
Subagents and Context Isolation
Each subagent starts with a clean context window, a restricted tool set, and a single bounded task. Isolation ensures a subagent reading files for one ticket cannot pollute the context of another.
Independent Review as Quality Architecture
When using one agent to review another's work, the reviewer must only be given the final output and the original specification. If the reviewer inherits the implementing agent's full conversation history, it becomes biased by the implementer's logic and ends up reviewing the reasoning rather than checking if the actual code meets the spec.
Parallel Execution and Specialization
Unlike a human team, an orchestrator can spawn multiple subagents to tackle independent tasks simultaneously (like running five different compliance checks at once). Subagents can also be specialized, using different system prompts or cheaper models suited to their specific bounded task, which optimizes both speed and cost.

Food for thought
  • What goes wrong when the orchestrator starts reading files and making implementation decisions instead of just coordinating?
    The orchestrator's context fills with implementation details (file contents, code decisions, task specifics), leaving less capacity for high-level coordination. As the window fills, coordination accuracy degrades and the orchestrator loses the overview it needs to route work and manage blockers effectively.
  • Why does a subagent need a clean context window and a bounded task? What breaks if it inherits the orchestrator's full context?
    A clean context window ensures the subagent only processes what's relevant. A single bounded task and a restricted tool set limit what the subagent can do, keeping its reasoning focused. If it inherits the orchestrator's full context instead, it receives coordination history, details from other tickets, and unrelated decisions, which pollutes its context, degrades accuracy, and risks cross-ticket interference.
  • Why does the reviewer see only the output and specification, not the implementer's conversation history?
    If the reviewer inherits the implementing agent's full conversation history, it becomes biased by the implementer's logic and ends up assessing the reasoning rather than the actual code. The review must independently judge whether the final output meets the spec, which is only possible if the reviewer starts with a clean context.
  • How do parallel execution and specialization improve the efficiency of a multi-agent system?
    Parallel execution allows an orchestrator to run multiple independent tasks simultaneously, drastically reducing wall-clock time. Specialization allows the orchestrator to route simpler tasks to cheaper, faster models while reserving expensive reasoning models for complex work, optimizing both overall cost and speed.
